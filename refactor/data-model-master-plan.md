## Executive Summary

This document defines the target data model architecture after Phase 2 implementation. It supersedes earlier design documents (2025-12-30, 2026-01-05, 2026-01-19) and reflects current implementation decisions. The model adopts **W3C PROV-O lite** principles with Entity-Attribute-Value (EAV) flexibility for evolving data types while maintaining typed product tables for core measurements.

## Core Architecture Changes by Phase 2

### What's Being Replaced
- **Legacy activity tables** (`samplingActivity`, `sampleProcessing`, `analysisActivity`, `workflowExecutionActivity`) → Unified `Activity` table with optional subtype tables
- **Implicit provenance** (foreign key chains) → Explicit PROV-O relationships via `Used` and `WasGeneratedBy` tables
- **Hardcoded sample processing links** → Flexible entity-to-entity derivations through activity chains

### What's Being Added
1. **Entity table**: Universal semantic layer - all "things" (samples, products, wells, protocols) get an entity_id
2. **Activity table**: Unified base for all timestamped actions (sampling, processing, analysis)
3. **Used table**: M:N relationship tracking which entities an activity consumed as inputs
4. **WasGeneratedBy table**: M:N relationship tracking which entities an activity produced as outputs
5. **Attribute + TypedAttributeValue tables**: EAV pattern for flexible, evolving metadata
6. **ActivityProtocol table**: Explicit storage for reusable procedure definitions (SOPs, workflows)

### Why These Changes
- **Flexibility**: New data types (ecoplates, metabolomics, XRF) don't require schema migrations
- **Provenance**: Explicit bidirectional tracking - trace any product back to original sample through activity chains
- **Recursion**: Support multi-step workflows where outputs become inputs (well → absorbance reading → nickel assay)
- **Non-redundancy**: Store experimental metadata once on entities; multiple timepoint measurements reference via relationships

## Information Flow Architecture

### 1. Sample Entry
```
Physical Sample → Entity (with entity_id) → Sample table (1:1 with Entity)
```
- Sample metadata in typed Sample table columns
- Evolving/experimental metadata in TypedAttributeValue (EAV)

### 2. Activity Execution
```
Activity (base table with activity_id, timestamps, activity_type)
  ↓
Optional: Activity subtype table (SamplingActivity, AnalysisActivity, etc.) for typed fields
  ↓
ActivityProtocol (linked via Entity) defines the procedure used
```

### 3. Entity-Activity Relationships
```
Input: Entity --[Used]--> Activity
Output: Activity --[WasGeneratedBy]--> Entity
```
- **Used**: Points FROM entity TO activity (this activity used these entities)
- **WasGeneratedBy**: Points FROM entity TO activity (this entity was generated by this activity)
- Same entity can be Used by multiple activities (e.g., well measured at 24h, 48h, 72h)

### 4. Product Generation
```
Activity --[WasGeneratedBy]--> Product Entity
  ↓
Product Table (ionAnalysisProduct, absorbanceProduct, metabolomicsFeatureTable, etc.)
  - 1:1 with Entity via entity_id foreign key
  - Typed measurement columns for queryable values
  - Additional metadata via TypedAttributeValue (EAV)
```

## Query Capabilities

### Supported Workflows
- **Linear chains**: Sample → DNA extraction → Sequencing → Assembly → Annotation
- **Recursive processing**: Sample → Ecoplate (96 wells) → Well A01 → Absorbance t=24h → Absorbance t=48h
- **Multi-input activities**: Well A01 + Well A02 → Combined nickel assay
- **Batch operations**: Single ecoplating activity generates 96 well entities simultaneously
- **Temporal series**: Same entity measured at multiple timepoints (non-destructive assays)

### Query Examples
1. **Provenance trace**: "Find all products derived from sample X"
   - Start at Sample entity → follow WasGeneratedBy chains through Activity nodes
   
2. **Method audit**: "Which samples were processed with protocol version 2.1?"
   - Join Activity → ActivityProtocol → filter by version → trace to Used entities
   
3. **Cross-batch comparison**: "Compare absorbance of wells with nickel > 1.0% across all plates"
   - Filter TypedAttributeValue for nickel_concentration_percent → join to Well entities → follow to absorbanceProduct
   
4. **Timepoint analysis**: "Get all measurements of well A01 from plate_01"
   - Query TypedAttributeValue for well_position='A01' AND batch_id='plate_01' → get entity_id → follow Used relationships → retrieve all absorbanceProducts

## PROV-O Implementation

### Adopted Relationships
- **Used**: Activity consumed Entity as input (many-to-many)
- **WasGeneratedBy**: Entity was produced by Activity (many-to-many)

### Not Implemented
- **WasDerivedFrom**: Redundant - derivation is implicit through Activity chains (Entity A --WasGeneratedBy--> Activity --Used--> Entity B)
- **WasInformedBy**: Not needed - activity chaining handled through entity passing

### PROV-O Semantics
- Activities represent timestamped actions in the world
- Entities represent persistent things (samples, measurements, files)
- Relationships are explicit, queryable, and bidirectional

## Metadata Storage Strategy

### Core Product Tables (Typed Columns)
**Use typed product tables when:**
- Measurement values are frequently queried/filtered (e.g., pH > 7.0, SO4-S concentration ranges)
- Cross-sample analytics require typed columns (statistical comparisons, aggregations)
- Data types are stable across workflow versions

**Examples:**
- `ionAnalysisProduct`: SO4_S_mg_per_kg, NO3_N_mg_per_kg, Cl_mg_per_kg
- `absorbanceProduct`: well_position, wavelength_nm, absorbance_value
- `metabolomicsFeatureTable`: mz, retention_time, peak_intensity, compound_id

**Protocol metadata for core products:**
- Method version, instrument ID → Stored in Activity or Activity subtype tables
- Static protocol details → ActivityProtocol table (linked via Entity)
- Run-specific parameters (dilution factors, QC notes) → TypedAttributeValue (EAV)

### Evolving or one-off Product Tables (EAV-heavy)
**Use EAV when:**
- Metadata schema is evolving or experiment-specific
- High cardinality (96 well positions, hundreds of peaks)
- Rarely queried directly (descriptive annotations, free text notes)

**Examples:**
- Well experimental treatments: nickel_concentration_percent, carbon_source
- Instrument settings: spray_voltage_kv, collision_energy
- QC annotations: analyst_notes, calibration_warnings

**Protocol metadata for evolved products:**
- Core method identity → Activity.activity_type ('ecoplating', 'XRF_analysis')
- Detailed protocol → ActivityProtocol referenced via EAV or Activity.protocol_id
- Experimental variations → TypedAttributeValue attached to Activity or Product entities

## Core Data Types (Implementation Targets)

### XRF Elemental Analysis
- **Product table**: `xrfElementalProduct` (element_symbol, concentration_mg_per_kg, qc_flag, detection_limit_mg_per_kg)
- **Activity type**: 'xrf_analysis' (just additive, not a new table)
- **Activity subtype table** (optional): `xrfAnalysisActivity` (instrument_name, beam_voltage_kv, measurement_duration_sec, matrix_correction_method, operator_id) - pending lab staff requirements
- **Protocol reference**: Vendor URL stored in ActivityProtocol table (simple 5-step protocol)
- **Migration**: Zero migration required - XRF slots directly into Phase 2 structure with new tables only

### LC-MS Metabolomics
- **Product tables**: 
  - `LCMSRawDataProduct` (file_format, scan_count, qc_status, acquisition_duration_sec) - maps to NMDC DataObject (mzML/vendor raw)
  - `LCMSFeatureProduct` (total_features, mz_range, rt_range, peak_picking_algorithm) - maps to NMDC DataObject (feature table)
  - `LCMSAnnotationProduct` (total_annotations, msi_level_counts, databases_searched) - maps to NMDC DataObject (annotation table)
  - `MetaboliteIdentification` (compound_name, kegg_id, msi_identification_level, confidence_score, peak_area) - maps to NMDC MetaboliteIdentification
- **Protocol tables** (reusable configurations, extend Entity):
  - `MassSpecProtocol` (acquisition_strategy, ionization_source, polarity_mode, mass_analyzers, resolution_categories) - maps to NMDC MassSpectrometryConfiguration
  - `ChromatographyProtocol` (chromatographic_category, stationary_phase, column_dimensions, flow_rate_ul_min, column_temp_celsius) - maps to NMDC ChromatographyConfiguration
  - `MobilePhaseSegment` (protocol_id, segment_order, duration_min, substance_name, concentration_value, concentration_unit) - maps to NMDC MobilePhaseSegment array
  - `CalibrationProtocol` (calibration_target, calibration_standard, internal_calibration) - maps to NMDC CalibrationInformation
  - `Instrument` (name, manufacturer, model, serial_number, institution) - maps to NMDC Instrument
- **Activity types**: 'lcms_acquisition' (maps to NMDC MassSpectrometry), 'lcms_feature_extraction', 'lcms_compound_identification', 'lcms_workflow_execution' (maps to NMDC MetabolomicsAnalysis)
- **Protocol linking**: Activities reference protocols via Used relationships with roles ('mass_spectrometry_configuration', 'chromatography_configuration', 'calibration_reference')
- **EAV metadata**: Run-specific instrument settings (spray_voltage_kv, capillary_temp_c), workflow parameters, GNPS identifiers
- **Migration**: Zero migration required - new protocol and product tables only; activities use existing Activity table with new activity_type values

### Ecoplates (96-well growth assays)
- **Product table**: `absorbanceProduct` (well_position, wavelength_nm, absorbance_value, measurement_date)
- **Entity type**: Well entities (no dedicated table - pure entity + EAV)
- **Activity types**: 'ecoplating', 'absorbance_reading'
- **EAV metadata**: batch_id, well_position, carbon_source, nickel_concentration_percent, timepoint_hours

### AMP2 Campaign (Automated Chained Workflows)
- **Product tables**: Varies by workflow step - may include flow cytometry cell counts, HPLC metabolite profiles, cultivation biomass measurements, isolation purity metrics
- **Activity types** (sequential, predictable chain): 'amp2_flow_cytometry', 'amp2_cell_isolation', 'amp2_cultivation', 'amp2_hplc_analysis', 'amp2_subculture', 'amp2_cryopreservation'
- **Protocol references**: Core protocol URLs linked via EAV (e.g., protocol_url='https://emsl.pnnl.gov/flow-cytometry-sop') or ActivityProtocol entities for standardized methods
- **EAV metadata**: Treatment-specific parameters (incubation_temp_celsius, cultivation_duration_hours, media_composition, substrate_concentration_mM, flow_rate_ml_min, detector_wavelength_nm)
- **Provenance pattern**: Sample → Activity1 → SubProduct1 → Activity2 → SubProduct2 → Activity3 → FinalProduct (explicit PROV-O chains via Used/WasGeneratedBy)
- **Key capability**: Same sub-product entity re-enters workflow multiple times (e.g., cultured cells measured at t=0, t=24h, t=48h, then subcultured → new activity → new measurements)
- **Workflow automation**: Activities are predictable and may be automatically triggered; actual instrument/treatment data captured in EAV per execution
- **Migration**: Zero migration - uses existing Activity table with new activity_type values; sub-products are entities tracked through explicit provenance chains

## Migration Strategy

### Phase 0 to 1 (Current)
- get permission to control things :)
- New data types → Entity + Activity + PROV-O + EAV from day one
- Existing data types → Continue using legacy tables (parallel systems)

### Phase 2 (Target)
- Activity subtype tables added for specialized typed fields
- Legacy activity data migrated to Activity + subtypes + Entity
- All new and backfilled data uses unified model

### Post-Phase 2
- Legacy tables deprecated
- Single API serving all data through Entity-Activity-PROV-O model
- EAV used exclusively for flexible/evolving metadata
